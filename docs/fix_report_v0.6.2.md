## ① 启动文件体检：内置规则先出结论，AI 分析必须手动点

- **诉求**：想有个「这个 bat 到底合不合理」的报告，但不愿意把数据随便发给模型。
- **改法**：新增 `src/launch_advisor.py`，「工具 → 启动文件 → 校验启动文件」对话框改成两页签：
  - **逐行解析**（原有能力，逐行讲每条参数干什么）
  - **合理性体检**：完全离线的规则引擎，查 7 类问题 —— 废弃/未知参数、重复参数、参数取值、上下文长度、显存需求、内存、磁盘余量。
- **AI 部分守三条底线**：
  1. 页面默认只跑内置规则引擎，**不点「让模型分析」按钮就不会调用任何模型**；
  2. 按钮只在**本机服务正在跑**时可点（用的是本机已经启动的那个模型），不发任何外部请求；
  3. 上送的 payload 里**不含 API Key**（构造时按参数名剔除），说明文案里写清楚送了什么。
  AI 失败不影响内置结论，提示语明确写了「与这条无关，仍然有效」。
- **验证**：`_check_advisor.py`（46 项）覆盖参数抓取、能力探测、KV 显存公式、payload 不含密钥、后台线程回调；`_check_validate_dialog.py`（27 项）覆盖双页签、后台体检不卡 UI、二进制文件跳过；`_check_ai_live.py` 用 `Qwen3-0.6B-Q8_0.gguf` 真起服务真跑一次，1.4 秒返回结构化报告。

## ② 表格横向铺满：拖过一列之后不再永久停止补宽

- **根因**：`src/ui/kit.py` 的 `ColumnResizer` 只要用户拖过**任意**一列，就永久放弃「补齐剩余宽度」，于是别的列宽一点就整表右边留白。
- **改法**：只有拖过**承担补宽的那一列**才锁定不再自动补（说明用户确实想自己定这一列），拖其他列仍然继续铺满。
- **验证**：`_test_layout.py` 新增断言；`_check_updater.py` 里「列表在筛选后仍铺满宽度」。

## ③ 启动命令区：拆解表与完整命令可拖分栏

## 顺手查出并修掉的 2 个真实 bug

### A. 新版 llama.cpp 删了 `--mlock` / `--no-mmap`，照旧硬写会启动失败

本机 `llama-server.exe`（b12810）的 `--help` 里**已经没有** `--mlock/--mmap/--no-mmap/--direct-io`：llama.cpp 0.4.1（2026-09）把它们合并成 `-lm/--load-mode`（取值 `auto / none / mmap / mlock / mmap+mlock / dio`）。旧启动文件带 `--mlock` 直接 `error: invalid argument` 起不来。

- `src/cmd_builder.py` 新增 `load_mode_args(mlock, no_mmap, exe)`：**以本机 `--help` 的能力为唯一依据**选写法 —— 新版出 `-lm mmap+mlock` / `-lm none` / 两个都勾出 `-lm mlock`，旧版仍出 `--mlock` / `--no-mmap`；结果按 exe 缓存（启动后 3 秒在后台预热，见 `src/ui/gpu_probe.py`）。
- `src/ui/bat_io.py` 从 bat 反推配置时能识别 `-lm` 取值回填勾选；两处 tooltip 同步说明「写法按本机版本自动选择」。
- `src/launch_advisor.py` 的体检把废弃参数直接给新写法（`--mlock 已被新版 llama.cpp 删除，请改用 -lm mmap+mlock`），而**本机是旧版时不给建议**，避免推荐一个本机同样不认的参数。
- **验证**：`_check_cmd_flags.py` 审计「启动器自己能生成的每一个 flag」在本机 508 项参数表里都存在，结果 0 个不认；`_v062_cases.py` 41 项钉住新旧两个分支。

### B. 官方包名解析：`ubuntu-26.04-s390x` 被判成「未知后端」

官方包名里会夹发行版版本号（`llama-b12811-bin-ubuntu-26.04-s390x.tar.gz`）和变体后缀（`android-arm64-snapdragon`），旧解析把它们当成后端名 → 纯 CPU 包被归到 `other`，勾「CPU」筛不到它们。

- `src/llama_updater.py` 解析后端时剔除架构词（`arm64`）、纯版本号段（`26.04`、`2026.4.1`）和变体后缀（`snapdragon`、`adreno`），剩下的段才拿去比对后端名。
- 用例全部改用 GitHub API 拉到的**真实资产名**（最近 6 个 Release 共 228 个资产里取的），不用猜的名字 —— `_v062_cases.py` 41 项里 14 组平台/后端组合逐条断言。

## 第二批用户反馈（6 条）

### ⑬ 能不能区分 MoE / 稠密？——能，而且三处都用同一个判据

- **模型信息页**早就显示「模型类型: MoE（128 个专家，每 token 激活 8 个）」/「稠密（Dense）」，判据是 GGUF 元数据里的 `expert_count` + `expert_used_count`。
- 本批把判据**做硬**：新增 `gguf_reader.expert_weight_map()`，直接读**张量表**按层累加专家权重实际字节（`ffn_*_exps` / `ffn_*_expert` / `.forward` / 带 `exp_b` 的 up/down/gate；路由器 `ffn_gate_inp` 与 `exp_probs_b` 不算专家），多分片模型逐片读再求和（每个分片的表只列自己装的张量）。本机实测对账：Inkling-2-Mini-Q4_K_XL 16.41 GiB 中专家 14.71 GiB（89.7%，24 层）、Flash-Next-Q4_K_XL 103.68 GiB 中专家 71.73 GiB（48 层）、Qwen3.8-27B 与 gemma-4-31B 专家 **0**。
- 有了逐层字节，界面（MoE 设置是否置灰）与命令行（参数是否下发）用的是同一条判据，不会两边说法不一。

### ⑭ 真 bug：稠密模型还带着 MoE 参数

- **现象**：Qwen3.8-27B（`expert_count=0`，稠密）启动命令行里出现 `--cpu-moe` / `--n-cpu-moe`。
- **根因**：`cmd_builder._moe_args()` 只看配置不看模型，而配置是**跨模型留存**的——上一个模型（Inkling 2）设过「前 N 层放 CPU」就一直在。
- **改法**：`_moe_args(s, model_path)` + `model_has_experts()`，稠密模型一个 MoE 参数都不下发；**探测失败（文件读不出）时不猜**，保留用户显式设置的值，不悄悄吞掉。界面上稠密模型整套 MoE 设置置灰并在下一行写明原因，且**不清空**用户原设置（切回 MoE 模型时还在）。
- 顺带把「思考强度是不是要配合 Agent」这条答疑写进文档（见 ⑯）。

### ⑮ MoE 专家参数预设：做成「目标预设 + 当场算」，不做 42 条静态组合

- 用户原提「按 7 档显存 × 6 档内存给组合预设」。这类死表帮不上忙：决定该卸几层的是**「这个模型的专家总量 − 你能给它的显存」**，同样 24 GiB 显存跑 Inkling 2（专家 14.7 GiB）该 N=0，跑 Flash-Next（专家 71.7 GiB）只能 `--cpu-moe`。硬件档位于是**进算法而不进选项列表**。
- 新增 `src/moe_advisor.py`：6 档目标（`auto` / 全放显存 / 平衡 / 省显存 / 极限省显存 / 长上下文优先），每档是一个显存水位 + KV 预留倍数 + 缓存份额；`plan()` 返回 `mode / N / cache / reason / facts`。
- **N 怎么算**：预算 = 显存 × 水位 −（非专家权重 + KV + 计算缓存），再解掉随 GPU 权重线性增长的计算缓存系数；然后**从最上层往下连续装**（`--n-cpu-moe` 只能卸前 N 层，而 UD 量化恰恰是上层专家更大），装不下即停 → N。UD 层间差一倍以上（Inkling 2 前 21 层 547 MiB、后 3 层 1033 MiB），所以「总量 ÷ 层数」必然算错，必须逐层。
- **缓存**：要卸载时先从预算匀出 `min(8 × 一层激活专家, 1 GiB)` 给 `--moe-cache-mib` 再重算 N；剩余显存连一层激活专家（专家 128 个 / 激活 8 个）都装不下时给 0，并在文案里说明「设了也白设」。
- **理由串摆数字**：显存 × 水位、非专家权重、KV、计算缓存、专家总量/层数/激活数、留了几层、缓存多少，用户可自行复核；`auto` 会额外说明选中了哪一档以及为什么。取不到显存或读不出模型时**直说取不到**（并后台补探测 `nvidia-smi`，补到后自动重算这一次），绝不编 N。
- 界面接线：`src/ui/moe_flow.py`（新）负责预设套用、稠密置灰、手动改任一项退回「不套用」、显存采样缓存（复用状态栏 `vram_raw_changed`，点预设零延迟）；`moe_preset` 持久化进 `config.py` / `config_io.py`；换模型后同一档自动重算（`ui/model_probe.py` 触发，扫描放后台线程不卡界面）。

### ⑯ 思考强度：服务级默认，Agent 可覆盖（答疑，已写进文档）

- 界面「思考强度」下发的是 `--chat-template-kwargs {"reasoning_effort": ...}`，作用于**该服务上所有未显式指定强度的请求**。
- Agent / 客户端在**单次请求体**里带同名字段时以请求为准，会覆盖界面档位——所以「界面选高、Agent 里选低」实际生效的是 Agent 的值。这一点与「联网查询/模型能力」页里检测到的 `reasoning_effort` 支持情况一致。

### ⑰ 命令预览「参数拆解」随窗口横向铺满

- **根因有两个**：`ColumnResizer` 的事件过滤器早于 `QAbstractScrollArea` 自身的 `resizeEvent`，直接补宽拿到的是**上一次**的 viewport 宽度（实测 1920 宽时列宽之和仍等于 1342 宽的值，最大化永远慢一步）；补宽目标又多加减了一次 `frameWidth`，等于凭空在右边留一条死边。
- **改法**（`src/ui/kit.py`）：Resize 后**延一帧**再补宽；目标改成 `viewport().width() - 1`；拖非补宽列之后重新补宽，拖过补宽列本身则不再自动改。
- **验证**：`_test_moe.py` 第 8 节用独立 `QTreeWidget` 覆盖首次显示、拉宽到 2560、缩回 900、拖非补宽列、拖补宽列五种情形，逐一断言列宽之和与 viewport 一致。

### ⑱ 运行日志清屏

- 「运行日志」页顶部加**清屏**与**打开日志目录**两个按钮（以前只能去菜单深处找「清空日志」）。
- 语义写清楚：**只清界面显示**，磁盘上按天存放的日志文件一个字都不动；清完在状态栏提示「磁盘上的日志文件仍然保留」。菜单项 `act_clear_log` 与按钮走同一个 `clear_run_log()`。
- 顺带给界面日志加 `setMaximumBlockCount(5000)`：服务长时间运行能刷到几十万行，全塞进控件会吃掉一大块内存（文件日志不受影响）。

### ⑲ 预测 Token / 批大小：预设 + 可自定义

- 新增 `src/ui/kit.py:NumberCombo`（照 `combo_ngl` 的可编辑下拉路线）：`value() / setValue() / valueChanged(int) / minimum() / maximum() / setRange()` 与 `QSpinBox` 同形，`QIntValidator` 钳位，档位文字可以带说明（如 `-1 = 无限输出`）；输入到一半的空串不改值也不发信号。
- `spin_np`：-1 ~ 1000000，档位 `-1 = 无限输出` / 1024 / 2048 / 4096 / 8192 / 16384 / 32768 / 65536；`spin_batch`：1 ~ 16384，档位 256 / 512 / 1024 / 2048 / 4096 / 8192。
- 现有代码（配置读写、边界测试 `_test_e2e_edge.py` 用 `spin_np.maximum()`）无需改动，直接兼容。

### 顺手修掉的第 3、4 个真 bug

- **`attention.head_count` 是数组时「合理性体检」直接崩**：Inkling-2 的该元数据是 24 个相同元素的数组，`gguf_reader._capture()` 原样收下来，`launch_advisor.model_profile()` 拿去参与运算抛 `TypeError`（即体检功能在 Inkling 上不可用）。新增 `_scalarize()`：全同取该值，不全同取最大值（宁可高估显存需求），并对非法元素返回 None。
- **多分片模型统计漏片**：每个分片的张量表只列自己装的张量（Flash-Next 4 片，第 1 片 72 条且不含专家），旧口径只看首片会把专家总量算成 0。`expert_weight_map()` 按 `_shard_group_files()` 逐片累加，并回报实际读到的片数。

## 已知边界（如实说明，不当成已实现）

- 显存/内存估算按「权重 + KV cache + 计算缓存」粗算：MoE 专家字节是**逐层实测**的（`moe_advisor`），但 KV 与计算缓存仍是经验系数，`--n-cpu-moe` / `--moe-cache-mib` 给的是「按本机资源尽量不放飞」的推荐值，不是实测吞吐承诺；多卡切分（`--tensor-split`）下专家缓存按卡分摊，也只给方向。
- 模型元数据缺 `context_train` 且脚本没写 `-c` 时，上下文那项只能说「未取到训练上限」，不编数字。
- 「让模型分析」的效果取决于本机当前跑的模型；小模型（如 0.6B）会给出方向正确但措辞粗糙的建议，内置规则表的结论始终是独立可看的。
