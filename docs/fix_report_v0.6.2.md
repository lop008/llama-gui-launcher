## ① 启动文件体检：内置规则先出结论，AI 分析必须手动点

- **诉求**：想有个「这个 bat 到底合不合理」的报告，但不愿意把数据随便发给模型。
- **改法**：新增 `src/launch_advisor.py`，「工具 → 启动文件 → 校验启动文件」对话框改成两页签：
  - **逐行解析**（原有能力，逐行讲每条参数干什么）
  - **合理性体检**：完全离线的规则引擎，查 7 类问题 —— 废弃/未知参数、重复参数、参数取值、上下文长度、显存需求、内存、磁盘余量。
- **AI 部分守三条底线**：
  1. 页面默认只跑内置规则引擎，**不点「让模型分析」按钮就不会调用任何模型**；
  2. 按钮只在**本机服务正在跑**时可点（用的是本机已经启动的那个模型），不发任何外部请求；
  3. 上送的 payload 里**不含 API Key**（构造时按参数名剔除），说明文案里写清楚送了什么。
  AI 失败不影响内置结论，提示语明确写了「与这条无关，仍然有效」。
- **验证**：`_check_advisor.py`（46 项）覆盖参数抓取、能力探测、KV 显存公式、payload 不含密钥、后台线程回调；`_check_validate_dialog.py`（27 项）覆盖双页签、后台体检不卡 UI、二进制文件跳过；`_check_ai_live.py` 用 `Qwen3-0.6B-Q8_0.gguf` 真起服务真跑一次，1.4 秒返回结构化报告。

## 顺手查出并修掉的 2 个真实 bug

### A. 新版 llama.cpp 删了 `--mlock` / `--no-mmap`，照旧硬写会启动失败

本机 `llama-server.exe`（b12810）的 `--help` 里**已经没有** `--mlock/--mmap/--no-mmap/--direct-io`：llama.cpp 0.4.1（2026-09）把它们合并成 `-lm/--load-mode`（取值 `auto / none / mmap / mlock / mmap+mlock / dio`）。旧启动文件带 `--mlock` 直接 `error: invalid argument` 起不来。

- `src/cmd_builder.py` 新增 `load_mode_args(mlock, no_mmap, exe)`：**以本机 `--help` 的能力为唯一依据**选写法 —— 新版出 `-lm mmap+mlock` / `-lm none` / 两个都勾出 `-lm mlock`，旧版仍出 `--mlock` / `--no-mmap`；结果按 exe 缓存（启动后 3 秒在后台预热，见 `src/ui/gpu_probe.py`）。
- `src/ui/bat_io.py` 从 bat 反推配置时能识别 `-lm` 取值回填勾选；两处 tooltip 同步说明「写法按本机版本自动选择」。
- `src/launch_advisor.py` 的体检把废弃参数直接给新写法（`--mlock 已被新版 llama.cpp 删除，请改用 -lm mmap+mlock`），而**本机是旧版时不给建议**，避免推荐一个本机同样不认的参数。
- **验证**：`_check_cmd_flags.py` 审计「启动器自己能生成的每一个 flag」在本机 508 项参数表里都存在，结果 0 个不认；`_v062_cases.py` 41 项钉住新旧两个分支。

### B. 官方包名解析：`ubuntu-26.04-s390x` 被判成「未知后端」

官方包名里会夹发行版版本号（`llama-b12811-bin-ubuntu-26.04-s390x.tar.gz`）和变体后缀（`android-arm64-snapdragon`），旧解析把它们当成后端名 → 纯 CPU 包被归到 `other`，勾「CPU」筛不到它们。

- `src/llama_updater.py` 解析后端时剔除架构词（`arm64`）、纯版本号段（`26.04`、`2026.4.1`）和变体后缀（`snapdragon`、`adreno`），剩下的段才拿去比对后端名。
- 用例全部改用 GitHub API 拉到的**真实资产名**（最近 6 个 Release 共 228 个资产里取的），不用猜的名字 —— `_v062_cases.py` 41 项里 14 组平台/后端组合逐条断言。

## 第二批用户反馈（6 条）

### ⑬ 能不能区分 MoE / 稠密？——能，而且三处都用同一个判据

- **模型信息页**早就显示「模型类型: MoE（128 个专家，每 token 激活 8 个）」/「稠密（Dense）」，判据是 GGUF 元数据里的 `expert_count` + `expert_used_count`。
- 本批把判据**做硬**：新增 `gguf_reader.expert_weight_map()`，直接读**张量表**按层累加专家权重实际字节（`ffn_*_exps` / `ffn_*_expert` / `.forward` / 带 `exp_b` 的 up/down/gate；路由器 `ffn_gate_inp` 与 `exp_probs_b` 不算专家），多分片模型逐片读再求和（每个分片的表只列自己装的张量）。本机实测对账：Inkling-2-Mini-Q4_K_XL 16.41 GiB 中专家 14.71 GiB（89.7%，24 层）、Flash-Next-Q4_K_XL 103.68 GiB 中专家 71.73 GiB（48 层）、Qwen3.8-27B 与 gemma-4-31B 专家 **0**。
- 有了逐层字节，界面（MoE 设置是否置灰）与命令行（参数是否下发）用的是同一条判据，不会两边说法不一。

### ⑭ 真 bug：稠密模型还带着 MoE 参数

- **现象**：Qwen3.8-27B（`expert_count=0`，稠密）启动命令行里出现 `--cpu-moe` / `--n-cpu-moe`。
- **根因**：`cmd_builder._moe_args()` 只看配置不看模型，而配置是**跨模型留存**的——上一个模型（Inkling 2）设过「前 N 层放 CPU」就一直在。
- **改法**：`_moe_args(s, model_path)` + `model_has_experts()`，稠密模型一个 MoE 参数都不下发；**探测失败（文件读不出）时不猜**，保留用户显式设置的值，不悄悄吞掉。界面上稠密模型整套 MoE 设置置灰并在下一行写明原因，且**不清空**用户原设置（切回 MoE 模型时还在）。
- 顺带把「思考强度是不是要配合 Agent」这条答疑写进文档（见 ⑯）。

### ⑮ MoE 专家参数预设：做成「目标预设 + 当场算」，不做 42 条静态组合

- 用户原提「按 7 档显存 × 6 档内存给组合预设」。这类死表帮不上忙：决定该卸几层的是**「这个模型的专家总量 − 你能给它的显存」**，同样 24 GiB 显存跑 Inkling 2（专家 14.7 GiB）该 N=0，跑 Flash-Next（专家 71.7 GiB）只能 `--cpu-moe`。硬件档位于是**进算法而不进选项列表**。
- 新增 `src/moe_advisor.py`：6 档目标（`auto` / 全放显存 / 平衡 / 省显存 / 极限省显存 / 长上下文优先），每档是一个显存水位 + KV 预留倍数 + 缓存份额；`plan()` 返回 `mode / N / cache / reason / facts`。
- **N 怎么算**：预算 = 显存 × 水位 −（非专家权重 + KV + 计算缓存），再解掉随 GPU 权重线性增长的计算缓存系数；然后**从最上层往下连续装**（`--n-cpu-moe` 只能卸前 N 层，而 UD 量化恰恰是上层专家更大），装不下即停 → N。UD 层间差一倍以上（Inkling 2 前 21 层 547 MiB、后 3 层 1033 MiB），所以「总量 ÷ 层数」必然算错，必须逐层。
- **缓存**：要卸载时先从预算匀出 `min(8 × 一层激活专家, 1 GiB)` 给 `--moe-cache-mib` 再重算 N；剩余显存连一层激活专家（专家 128 个 / 激活 8 个）都装不下时给 0，并在文案里说明「设了也白设」。
- **理由串摆数字**：显存 × 水位、非专家权重、KV、计算缓存、专家总量/层数/激活数、留了几层、缓存多少，用户可自行复核；`auto` 会额外说明选中了哪一档以及为什么。取不到显存或读不出模型时**直说取不到**（并后台补探测 `nvidia-smi`，补到后自动重算这一次），绝不编 N。
- 界面接线：`src/ui/moe_flow.py`（新）负责预设套用、稠密置灰、手动改任一项退回「不套用」、显存采样缓存（复用状态栏 `vram_raw_changed`，点预设零延迟）；`moe_preset` 持久化进 `config.py` / `config_io.py`；换模型后同一档自动重算（`ui/model_probe.py` 触发，扫描放后台线程不卡界面）。

### ⑯ 思考强度：服务级默认，Agent 可覆盖（答疑，已写进文档）

- 界面「思考强度」下发的是 `--chat-template-kwargs {"reasoning_effort": ...}`，作用于**该服务上所有未显式指定强度的请求**。

### ⑰ 命令预览「参数拆解」随窗口横向铺满

## 第三批（续修）：微批 -ub 与「启动即显存分配失败」

### ⑳ 结论先行：小模型 + 大微批 + 长上下文，确实能把显存吃光

不是传闻，也不是「权重太大」。本机用 **Qwen3-0.6B Q8_0（0.6 GiB）**，读 llama-server 自己打印的 `CUDA0 compute buffer size`（与外机进程无关）：

| 条件 | 计算缓冲 |
| --- | --- |
| `-c 8192`，`-ub` 128 / 256 / 512 / 1024 / 2048 / 4096 | 73 / 146 / 292 / 584 / 1168 / 2336 MiB |
| `-ub 512`，`-c` 2048 / 4096 / 8192 / 16384 / 32768 | 88 / 156 / 292 / 564 / 1108 MiB |
| `-c 32768 -ub 2048`（关 FA） | **4432 MiB** |
| `-c 32768 -ub 512`（开 FA） | 58.5 MiB |
| `-c 32768 -ub 2048`（开 FA） | 232.6 MiB |
| `-c 8192 -ub 512`，`-np 2 / 4` | 156 / 88 MiB |

即：**同一个模型，只改微批与上下文，计算缓冲能从 58 MiB 涨到 4.4 GiB（76 倍）**；权重一点没变。这也解释了为什么 `-c 8192` 时同样配置只有 1.1 GiB —— 真正致命的是**长上下文 × 大微批**，而不是「4B 模型 + 8K」。

> 说明：这条结论是用**本机 0.6B 模型**逐点量出来的，其它模型按 KV 头数线性缩放（公式里只有 KV 头、微批、上下文三个量）。我没有把「某个具体 issue 的 12 GB 现场」当成已复现的结论——那台机器的权重/KV/其它进程占用都不同，不能替我背书。

### ㉑ 启动器以前根本不下发 `-ub`

- `cmd_builder` 只发 `-b`，`-ub` 只能靠导入 `.bat` 带进来；界面既看不见也拦不住。
- 现在：`config.py` 增 `ubatch`（默认 512 = llama.cpp 默认值），生成参数第 2 行加「微批(-ub)」档位下拉（64…2048，可自定义），`cmd_builder` 下发 `-ub` 并**强制 ≤ `-b`**（引擎侧同一硬约束），导入 `.bat` 时认 `-ub/--ubatch-size` 回填。

### ㉒ 估算模型：`attn_scratch_gib()`（15 点实测，最大偏差 3.7%）

```
关 FA：MiB ≈ 微批 × (8 × KV头 × 上下文 / 2²⁰ × 1.06 + 0.04)
开 FA：上下文项 × 0.031，另有每 token ≈ 0.053 MiB 固定开销
```
- 系数全部来自上面那张表，且**刻意偏保守**（开着 FA 时高估 1~3%，宁可多提示不误放行）。
- `-np > 1` 时真实值会更小（slot 会再分摊微批），估算**不折算**，属安全侧。
- `memory_budget()` = 权重 + KV（沿用既有公式，实测 ctx 8192 → 896 MiB 与公式**一分不差**）+ `max(激活, 权重×12%)`。

### ㉓ 启动前预算：只提示 + 一键下调，绝不静默改

- `start_server` 在 `build_args` **之前**调用 `_prelaunch_vram_check()`：用 `probe_vram_free_mb()`（**可用**显存，不是总量）比预算，留 3% 给驱动/碎片。
- 超了就弹窗：三项数字 + 「按建议改微批并启动（`suggest_ubatch()` 从 2048 往下找能装下的最大档）」/「仍然启动」/「取消」；文案写明**这是估算，不是保证**。
- 取不到显存（nvidia-smi 失败）→ **不弹窗、不拦**，交给体检页。
- 与 MoE 预设同一条原则：**能算就摆数字，算不出就直说，不替用户拍板**。

### ㉔ 体检页新增「批处理峰值」

- 单独一项：`批处理激活约 X GiB：微批 -ub N × 上下文 C（KV 头 H，闪存注意力 关/开）`，≥1 GiB 标黄。
- 关 FA 且上下文 ≥8K 时直接建议 `-fa on`；否则建议把 `-ub` 降到 256~512。
- 「显存需求」那项的提示也改成按见效快慢排序：先微批/FA，再上下文/slots，最后 ngl/量化。

### 验证

- `_test_membudget.py` 37 项：15 个实测点对账、`memory_budget` 组成与钳位、`suggest_ubatch`（含「降到 64 也装不下 → 返回 None」）、`-ub` 下发与钳位、体检项文案、界面控件/配置往返/导入 bat、启动前弹窗三种选择（用假 QMessageBox 离屏驱动，不真弹窗）。
- 注册进 `_test_all.py` 为 `membudget` 套件。

### 明确没做的（避免误导）

- **没有**「自动调 `-b` 防止 OOM」这种能力：显存分配受驱动、碎片、其它进程影响，任何「自动」承诺都不可靠。给的是**估算 + 建议值 + 一键应用**。
- **没有**强制 `-np 1`：KV 占用是实打实的，但把并发砍到 1 会影响 Agent 使用；只在超预算时把「减小 -np」列进建议。
- **没有**替用户改 `-c`：上下文是用户的核心选择，只提示。

## 第四批（续修）：启动器自升级——从「能用」到「失败也不闯祸」

### ㉕ 先回答「自升级做了没有」：做了，而且是完整链路

不是空壳，代码在 `src/launcher_updater.py` + `src/ui/launcher_update_dialog.py`：

| 环节 | 已有能力 |
| --- | --- |
| 入口 | 菜单「关于 → 检查启动器更新…」 |
| 静默检查 | 启动后 6 秒后台查一次（`main_window.py`），**不弹窗**：只把窗口标题加上 `· ⬆ vX.Y.Z`，状态栏提示 12 秒 |
| 开关 | 基础页「启动时检查启动器更新」，存 `config.json` 的 `check_launcher_update`，默认开 |
| 比版本 | `parse_version` 处理 `v` 前缀、缺省 patch、`beta/rc` 排在正式版之前（实测 9 组边界正确） |
| 挑包 | `host_arch()` 认 ARM64（连 32 位进程跑在 ARM 上的 `PROCESSOR_ARCHITEW6432` 也探），x64/arm64 分别匹配 |
| 下载 | 后台线程 + 进度条 + 可取消；`.part` 断点续传（带 `Range`，处理 416） |
| 替换 | 生成独立 `.bat`：等本进程退出 → 旧 exe 备份 `.bak` → 覆盖 → 重启 → 自删脚本 |
| 兜底 | 源码运行（`python main.py`）不换自己，改为打开 Release 页；只有 zip 时提示手动下载 |

事实补充：截至本轮，GitHub 上最新发布仍是 **v0.6.0（2026-11-27）**，本地 0.6.2 未推送未发布——所以「已装用户能升到 0.6.2」要等发布之后才成立。

### ㉖ 实测复现出一个能弄丢用户程序的缺陷

老版 `schedule_replace` 生成的 bat 只有三条 `move`，**一处 errorlevel 判断都没有**。我把脚本拿临时假文件真跑了一遍（模拟「下载完的新 exe 被安全软件隔离」——未签名新 exe 被 Defender 实时保护吞掉是日常）：

```
=== 结果 ===
  LLama-Launcher-win-x64.exe.bak     9 字节  内容='OLD-BUILD'
用户的「双击 exe」入口还在吗: False
```

旧 exe 已经被改名成 `.bak`，第二条 `move` 搬的是不存在的文件（照样失败），第三条 `start` 也照样执行。用户视角就是「点了升级，软件打不开了」，而数据其实在 `.bak` 里，只是没人会知道。`schedule_replace` 里那句 `if not os.path.isfile(new_exe)` 只在**生成脚本那一刻**查一次，防不住这种情况。

### ㉗ 修法：每步判错、自动回滚、结果留痕

新 bat 的成功路径与失败路径都各自真跑验证：

- 每一步 `move` / `xcopy` 后立刻 `if errorlevel 1`，按失败种类写不同标记码。
- **回滚**：任何一步失败都把 `.bak` 改回去；回滚成功时**保留失败原因**标记（只有回滚也失败才升级为 `fail_rollback`，那时才提示用户手动改文件名）。
- 失败时**绝不 `start`** 一个可能不存在的 exe。
- 等 PID 退出那段加了次数上限（约 60 秒），不会因为误判永久卡住。
- 结果只写 **ASCII 标记码**（`ok` / `fail_locked` / `fail_copy_internal` / `fail_move_exe` / `fail_internal_locked` / `fail_rollback` / `pending`）到临时目录的 `llama_launcher_update_result.txt`，避免 bat 写中文的编码坑；界面 `report_last_self_update()` 下次启动读一次并翻成当前语言（状态栏 + 运行日志），**读一次即清**，不会天天提醒。

单文件版的回滚**不复用**便携版那段（后者会清 `_internal`）——测试里专门有一条：单文件 exe 的目录里如果本来就放着别人的 `_internal`，回滚后必须完好。

### ㉘ 下载完要验货，坏文件不许进替换流程

`verify_download()`：大小与 GitHub 报的 asset size 比对（API 一直有给，以前没用）+ 文件头检查（exe 查 `MZ`，zip 查 `PK` 且 `is_zipfile`）。不过就直接删掉、报原因，**根本不生成替换脚本**。

断点续传也补了防串：`.part` 旁边记一个 `.meta.json`（存 URL）。URL 变了（Release 被重新上传过同名文件）或者已有部分**比预期大小还大**，就丢弃重下——否则旧半截拼新半截正好产出 ㉖ 那种坏 exe。

另外 `disk_space_ok()`：便携包要同时容下 zip + 解压后的 `_internal`（约需 3 倍体积），不够就在点下载之前说清楚，而不是下到一半失败。

### ㉙ 便携版不再被换成单文件包

`install_kind()` 按「exe 旁边有没有 `_internal`」区分 `single` / `portable` / `source`（PyInstaller onedir 必然带 `_internal`）。老逻辑一律优先 `.exe`，于是**便携目录用户会被推单文件包**：覆盖后能跑，但 `_internal` 变成几十 MB 垃圾，启动还慢一截（实测本机 `dist/` 里便携 exe 只有 5.95 MB，单文件包 47 MB）。

现在 `pick_asset(release, arch, kind)` 按形态分流：便携优先 `-portable.zip`，单文件优先 `.exe`；目标形态没打包时退而求其次，并在徽标上写明「便携包缺失，将改用单文件版」。

便携包的替换走「先解压备齐，再只搬运」：`extract_package()` 把 zip 解到临时 stage，**不照搬 zip 里的顶层目录名**——那层名字是中文（`LLama启动器-win-x64-portable/`），而 PyInstaller 写 zip 没置 UTF-8 标志位，`zipfile` 按 cp437 解出来是乱码，路径根本没法用；改成按「`.exe` 结尾」与「`_internal/` 之下」两类逐条落盘。bat 只负责：挪旧 exe → 旧 `_internal` 改名 `.old` → `xcopy` 新 `_internal` → 放新 exe → 清理 `.old`/`.bak` → 启动；**用户自己的 `config.json`、`logs/`、`stats.json` 一个都不碰**（测试逐条断言）。

对话框新增「安装形态: 单文件版 / 便携目录版（exe + _internal）/ 源码运行」，tooltip 说明升级会不会动依赖、用户数据动不动。

### 验证

- 新增 `_test_selfupdate.py` **62 项**，注册为 `_test_all.py` 的 `selfupdate` 套件（现 20 套件）。关键项都是**真跑**：成功替换 / 新文件消失后回滚 / 旧 exe 被占用（用不带 `FILE_SHARE_DELETE` 的文件句柄锁住，rename 必然失败）/ 便携版整包替换并核对用户数据未动 / 单文件回滚不误删 `_internal`。
- 解压用合成 zip（中文顶层目录）+ **真实发布包** `dist/LLama启动器-win-x64-portable.zip` 各跑一遍。
- `pick_asset` 兼容旧调用形式（只传 arch），既有 `_test_v06.py` 4 条断言不破。
- i18n：30 条新增界面文案译入 7 张表并清掉 4 条失效；各表 **1199 条，缺失 0、多余 0、`_i18n_validate.py` PASS**。

### 明确没做的（避免误导）

- **没做代码签名**：那是发布层面的事，且自升级路径下未签名 exe 被杀软拦是真实风险，所以现在只能「失败可回滚 + 报得清楚」，不能假装不存在。
- **没做哈希来源**：GitHub asset 本身不提供官方 sha256，要更强校验得在 Release 里附带校验文件并信任链，这轮先用「大小 + 文件头 + 解压可完成」兜住明显损坏。
- **没有静默自动安装**：仍是用户点一次「下载并安装」，退出前再确认一次。自动替换别人的程序风险大于收益。
- **没动 llama.cpp 的更新页**：`updater_tab.py` 那套（含 `schedule_self_update`，用于 llama.cpp 自身二进制）是另一条链路，本轮只改启动器自身的升级。

## 已知边界（如实说明，不当成已实现）

- 显存/内存估算按「权重 + KV cache + 计算缓存」粗算：MoE 专家字节是**逐层实测**的（`moe_advisor`），但 KV 与计算缓存仍是经验系数，`--n-cpu-moe` / `--moe-cache-mib` 给的是「按本机资源尽量不放飞」的推荐值，不是实测吞吐承诺；多卡切分（`--tensor-split`）下专家缓存按卡分摊，也只给方向。
- 模型元数据缺 `context_train` 且脚本没写 `-c` 时，上下文那项只能说「未取到训练上限」，不编数字。
- 「让模型分析」的效果取决于本机当前跑的模型；小模型（如 0.6B）会给出方向正确但措辞粗糙的建议，内置规则表的结论始终是独立可看的。
